# カード作成要件Issueの原案（起票済み）

## タイトル

Recall Cardのカード作成フロー改善要件を整理する

## 目的

選定した「B スレートグレー」のデザインを前提に、テンプレート選択からカード保存までの操作負担を整理し、実装範囲と受け入れ条件を確定する。

このIssueは要件整理のみ。アプリ実装・DB変更・認証変更は行わない。

## 対象フロー

テンプレート選択 → コピー → 外部AIで整形 → 回答貼付 → 解析結果の確認・編集 → 保存。
整形済みの回答を持つ利用者が、テンプレート選択を経由せず作成できる経路も扱う。

## 整理する内容

- 現行の画面遷移・操作と、その根拠となるコード・撮影画像・Spec。
- 初回利用者と、回答をすでに持つ利用者の入口。
- 一覧から直接コピーする案と、詳細経由を維持する案の比較。
- 原文、編集欄、解析時点のMarkdown表示、任意メモ・タグの表示範囲。
- 再解析で置き換える項目、編集済み内容・入力値の保持。
- コピー失敗、空入力、形式崩れ、保存失敗、通信中の表示・復帰。
- キーボード、フォーカス、モバイル操作、未ログイン・他ユーザーの境界。
- 各変更を#130で扱うか、別実装Issueへ分けるか。

## 対象外

- 検索条件保持・復習操作の詳細設計（別途優先順位を決める）。
- デザインの再選定、AI API、Google認証、DB構造変更、新ライブラリ導入。
- 自動保存、既存validationや認可の緩和。
- このIssue内でのアプリ実装、commit、push、PR作成。

## 完了条件

- 現在と変更後のフローを比較できる。
- 各提案に採用／見送り／保留と理由がある。
- 通常・エラー・送信中・再操作時の振る舞いを整理する。
- 入力保持・保存有無・認証認可に関する受け入れ条件を定義する。
- PC／モバイルの画面構成と確認方法が分かる。
- 実装対象・対象外、変更候補ファイル、必要なSpec・手動確認を整理する。
- #130との重複を整理し、実装単位へ振り分ける。

## 前提

- #129で選定したB スレートグレーと共通部品方針を使用する。
- current_userによる分離、Markdown無害化、CSRF、保存前確認を維持する。
- AGENTS.mdを優先する。マージはユーザーが行う。

※ユーザー承認により#136として起票済み。起票時の確定本文はreview-issues/creation.md、全体の担当範囲はreview-issue-index.mdを参照。このファイルは原案として保持する。
