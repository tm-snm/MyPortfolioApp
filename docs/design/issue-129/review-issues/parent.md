## 目的

#129で選定した「B スレートグレー」を基に、画面・操作・仕様の簡略化と品質向上の検討をジャンル別に管理する。ユーザーの明示指示により起票する。

**カード作成フローを最優先**とする。すべての子Issueを同時に実装したり、新しい本リリース必須条件へ自動追加したりしない。課題の根拠・ユーザー価値・負荷から採否と順序を決める。

## 役割分担

- #129: 選定結果・共通部品・大まかなコア導線・状態表示の確定。本Issue起票をもって完了やクローズにはしない。
- 本親Issueと子Issue: 詳細な見直し要件、確認観点、採用／見送り、実装への分割。
- #130: 選定デザインの適用。子Issueで合意した変更のうち範囲に入るものだけ実装する。
- #128: 認証・認可・CSP等のセキュリティ対策と回帰確認。重複した監査Issueは作らない。
- #100: README・本番QA・リリース。評価計画から結果と未確認事項を引き継ぐ。
- #96: Google認証は延期を維持。完了済み#85/#99等は再オープンしない。

## 優先順位と依存関係

1. #129の共通仕様を整理しながら、カード作成要件を最優先で検討する。
2. 同じ画面に影響する情報整理・状態表示・モバイル要件を整合させる。
3. 検索・閲覧・復習・ダッシュボード等は後続。採用範囲は実装前に確定する。
4. #130着手前には#128の対策状況を確認する。影響する要件を未決定のまま画面実装して手戻りを増やさない。

## 調査の根拠と限界

#129の現行撮影16枚・コード・Spec調査と、それに基づく改善候補が出発点。
ローカル資料: docs/design/issue-129/current-state.md、hybrid-ux-plan.md、selection.md（未コミットのためGitHubからはまだ閲覧できない）。
未撮影画面・実機・性能・利用者理解は子Issueで確認する。現時点で全問題を発見済み、適合済み、改善効果が実証済みとは扱わない。

## 共通の進め方・制約

- 本Issueは**調査・比較・要件整理**が成果物。修正案は採用決定ではない。採用／見送り／保留と理由を記録する。
- 観測済みの課題、コードからの確認事項、未検証の仮説を区別する。未撮影箇所は実画面を確認してから判断する。
- #129で選定した「B スレートグレー」を前提にする。配色・デザインの再選定は行わない。
- 実装する場合は#130との担当範囲を照合し、必要に応じて別実装Issueへ切り出す。実装・DB変更・本番操作をこの起票だけで承認済みにしない。
- AGENTS.mdと現在のコード・schema・Specを優先。既存Rails/ERB/Bootstrap/Turbo/Stimulus/importmapを維持し、新Gem/npm・AI API・Google認証を前提にしない。
- current_userによるデータ分離、Markdown無害化、CSRF、入力検証・保存前確認を維持する。簡略化のために弱めない。
- 架空データを使用し、秘密値・本番データ・認証情報をIssue・画像・ログへ記載しない。
- 実装時は1 Issue = 1ブランチ = 1PR。ユーザーの指示に従い、実装→対象テスト→全体テスト→RuboCop→git diff→結果報告で停止。commit/push/PRは別指示、マージはユーザーが行う。
